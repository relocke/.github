# Contributing to ReLocke

Thank you for helping build infrastructure for open systems. ReLocke welcomes implementation work, specifications, documentation, examples, integrations, design research, and constructive technical discussion.

## Before contributing

1. Search the target repository's issues and discussions for related work.
2. Open an issue before beginning a large or compatibility-sensitive change.
3. Keep proposals focused on a concrete user, ecosystem, or interoperability problem.
4. Document security assumptions and trust boundaries when work consumes repositories, builds, metadata, network data, or machine-generated content.

## Pull requests

- Keep each pull request narrow enough to review safely.
- Explain the problem, the chosen approach, alternatives considered, and validation performed.
- Include tests or examples for behavior changes.
- Preserve backward compatibility unless the proposal explicitly introduces a versioned breaking change.
- Do not commit credentials, private keys, access tokens, customer information, or unlicensed third-party assets.

## Specifications and schemas

Interface proposals should include:

- a motivating use case;
- a versioning and compatibility strategy;
- normative field definitions;
- at least one complete example;
- validation and failure behavior;
- trust and security considerations; and
- a path for adoption by existing software.

## Community

Participation is governed by the [Code of Conduct](CODE_OF_CONDUCT.md). Security vulnerabilities should be reported according to [SECURITY.md](SECURITY.md).
